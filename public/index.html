旧连接处置策略

延迟与补齐成本的显式取舍

overlap — 让两路短暂重叠

旧连接一降级，新连接立即接管；旧连接迟到补发的尾部内容被当作暂定收下，再用按序号补取确证。接收延迟最低，代价是尾部帧可能带错内容，必须过一次裁决与确证。

hold — 先停旧连接再补取

先用状态通知把旧连接退休，它随后的尾部帧按身份规则拒收；洞只能靠按序号补取填。没有重叠、没有尾部猜测，代价是补齐成本更高，且这段时间的号一直缺着。

连接身份台账

每个 socket 一个 epoch，一个 basis 声明
连接角色epochrelease → global覆盖帧状态
身份与业务顺序如何分开保存

connections 只存身份：conn_id · epoch · basis_key · 状态。它不知道任何业务进度。

coverage 只存业务顺序：每个 global 一条，记住是哪一帧、什么等级（firm / tentative）。它不知道帧来自哪条连接的身份语义。

frames 把两者连起来：一帧同时携带 conn_id + epoch + release。重编号只会改变后者的解释，不会改写已落定的 global。

为什么这些数字是分开的

三个库，三种失败

receiver.db — 连接身份、帧、覆盖、冲突。接收器崩溃只会丢“尚未确认的帧”，不会改写已落定的号。

backfill.db — 会话台账、已验证过的区间。补取器重启后知道哪些区间已经补过，不会重复付成本。

lander.db — 批次、落盘行、修订记录。入库器崩溃后靠 staging / committed / acked 三态恢复：未提交的整批回滚，已提交未确认的逐行核对后再确认。

身份与顺序不是一回事

release 只是某条 socket 在某 epoch 上的计数。它能变成 global，只因为源端在该 socket 的 hello 里声明了 basis（releaseStart → globalStart）。

没有 basis 的帧一律隔离，绝不猜位置；epoch 对不上也隔离。所以“旧连接还在发”只会污染它自己的编号空间，不会改写新连接的业务顺序。

两种“完整”，不要混用

receivedComplete — 每个号都有内容，且游标从 1 连续。tentative 也算有内容。

verifiedComplete — 每个号都是 firm：没有尾部猜测、没有待裁决冲突。

“足以确认完整”还要再加两条：所有行都已 acked，且与源端清单逐号一致、全流指纹一致。
